# Impact analysis: мультивалютный сплит

## 1. Бизнес-требование

Представлять одну финансовую операцию несколькими составляющими с разными суммами и валютами. Действующие потребители должны продолжать получать необходимые им данные. Переходный период параллельной поддержки старых клиентов — 9 месяцев.

## 2. Затронутые части контракта

| Часть контракта | Затронута? | Почему |
|---|---|---|
| `Money` | **Да** | В общую переиспользуемую схему добавлено новое опциональное поле `precision` для поддержки расширенных настроек округления. |
| `OperationListItem.amount` | **Нет** | Структура и ссылка на `$ref: '#/components/schemas/Money'` сохранены без изменений для обеспечения обратной совместимости в контуре `/v1/`. |
| `OperationDetail` | **Нет** | Наследует `amount` через `allOf` от `OperationListItem`. Формат и обязательность полей для CRM-системы в `/v1/` не меняются. |
| `OperationDetailV2` | **Да** | Новая схема-наследник, созданная для реализации мультивалютного сплита. Содержит обязательный массив `splits`. |
| `SplitObject` | **Да** | Новая изолированная схема, описывающая атомарную составляющую сплит-операции (`splitId`, `amount`, `currency`). |
| `ApplyDecisionRequest` | **Нет** | Операция корректировки скорингового решения в CRM не использует сущность `Money` и не зависит от финансового сплита. |
| `Error` / `ErrorResponse` | **Нет** | Корпоративная модель ошибок универсальна и не затрагивается изменениями бизнес-логики. |

## 3. Затронутые consumers

| Consumer | Что читает | Прямой impact? | Почему |
|---|---|---|---|
| Mobile | `OperationListItem.amount`, `.status`, `.createdAt` | **Да** | Прямой импакт при переходе на новые сценарии. Добавление опционального `precision` в `Money` безопасно, но для отображения сплитов приложение должно будет мигрировать на эндпоинт `/v2/`. |
| CRM | `OperationDetail.customer`, `.audit`, `.merchant`, `.scoringDecision`, `.amount` | **Да** | Читает унаследованную сумму `Money`. Изменение схемы `Money` (добавление `precision`) не ломает чтение детальной информации в CRM-контуре. |
| Analytics | `OperationListItem.status`, `.createdAt`, `.id` | **Нет** | **Компонент Money не читает.** Финансовые сплиты, изменения типов данных или состава полей внутри объекта `Money` никак не влияют на аналитический контур. |

## 4. Классификация изменений

| Изменение | Structural / Semantic | Breaking? | Почему |
|---|---|---|---|
| Добавление опционального поля `precision` в `Money` | **Structural** | **Нет** | Добавление необязательного поля (отсутствует в `required`) признается обратно совместимым расширением контракта. |
| Внедрение массива `splits` с обязательными полями в `OperationDetailV2` | **Structural** | **Да (для старой версии)** | Если бы массив `splits` был внедрен в существующий эндпоинт `/v1/` взамен плоского `amount`, это бы полностью разрушило парсинг у старых клиентов. Изменение изолировано в рамках `/v2/`. |
| Агрегация мультивалютных сплитов в одну сумму для клиентов `/v1/` | **Semantic** | **Да** | Изменяется бизнес-смысл возвращаемой суммы на `/v1/`: теперь это расчетное/агрегированное значение (требуются явные правила конвертации валют). |

## 5. Варианты решения

| Вариант | Совместим с v1? | Удовлетворяет бизнес-требованию? | Риски |
|---|---|---|---|
| **Совместимое расширение** (добавление массива `splits` как optional-поля в текущий контракт `/v1/`) | Да | Нет | Не решает задачу разделения операций на уровне списков. Старые клиенты будут игнорировать массив, а новые не смогут валидировать данные, если сервер пришлет пустой сплит. Разрушается REST-семантика. |
| **Новая мажорная версия** (`/v2/`) | Нет (внутри `/v2/`) | Да | Требуется развертывание слоя трансформации данных (Compatibility Adapter) и одновременная поддержка двух версий API в течение 9 месяцев. |

## 6. Выбранное решение

**Вариант:** Выпуск новой мажорной версии API с Path Versioning (`/v2/`) при сохранении полной работоспособности `/v1/` эндпоинтов.

**Обоснование:** Изменение структуры финансовой операции с плоской модели на массив сплитов является критическим ломающим изменением (*Breaking Change*). Согласно п. 3.4 стандарта банка, любые обратно-несовместимые изменения обязаны реализовываться через выпуск новой мажорной версии.

**Стратегия versioning/migration:**
1. В инфо-блоке спецификации фиксируется SemVer `2.0.0`. Мажорная версия отражается в URI путей: `/v2/accounts/{accountId}/operations`.
2. Существующие универсальные эндпоинты `/v1/` продолжают функционировать без изменений на протяжении 9 месяцев.
3. На уровне API Gateway разворачивается *Compatibility Adapter*. Для старых клиентов `/v1/` он агрегирует мультивалютные сплиты из единого лога событий АБС в одно денежное значение по правилам банка.

**Что меняется в контракте:**
* В `components/schemas` добавлены новые модели `OperationDetailV2` и `SplitObject`.
* В `components/schemas/Money` добавлено опциональное поле `precision`.
* Добавлен новый путь `/v2/accounts/{accountId}/operations`, возвращающий массив `OperationDetailV2`.
* Старые пути `/v1/` и связанные с ними схемы (`OperationListItem`, `OperationDetail`) сохранены в исходном виде.

## 8. Аргументы для review

* **Почему выбрано это решение?** Защищает продуктовый контур от аварийного завершения работы мобильных приложений v1 при изменении структуры ответа, строго соблюдая стандарт OpenAPI Governance банка.
* **Какие последствия для consumers?** Потребители Mobile и CRM получают возможность постепенной бесшовной миграции на `/v2/` в течение 9 месяцев. Для потребителя Analytics изменения прозрачны, так как он не зависит от схем `Money`/`splits`.
* **Как обеспечивается переходный период 9 месяцев?** За счет параллельного существования эндпоинтов `/v1/` и `/v2/` в одном YAML-контракте и слое трансформации данных на API Gateway.
